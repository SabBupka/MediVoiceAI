# Локальный голосовой ассистент регистратуры

Локальный MVP голосового ассистента для тестового стенда «Регистратура».
На первом этапе проект работает без внешнего SIP-транка и без реальных
телефонных номеров: телефонный контур воспроизводится локальными HTTP API и
текстовыми сессиями. Позже этот слой можно заменить на Asterisk/SIP без
переписывания бизнес-логики.

## Демо продукта

Демо-скрипт `scripts/demo_checkpoint.ps1` показывает полный тестовый сценарий
записи к терапевту: распознавание намерения, подбор врача и свободного слота из
расписания, диалог подтверждения, создание пациента и визита, проверка
результата через API. Скрипт печатает HTTP-методы и пути, реплики и ответы.
Он проверяет `GET /health` и работает только при `registry_mode=mock`.

```powershell
.\scripts\demo_checkpoint.ps1
```

Для показа скрипт использует синтетическую карточку «Демо Тест» и создаёт
тестовый визит в локальном mock-реестре. Это запись в демонстрационных данных,
не во внешнем стенде. Скрипт берёт первого подходящего врача и свободный слот
из `GET /api/doctors` и `GET /api/slots`; поэтому перед запуском должно быть
загружено расписание.

В текущей реализации `POST /api/voice/process-text` сначала применяет правила
безопасности и распознавания; если намерение не определено, локальная LLM
классифицирует его. Затем скрипт показывает отдельный API-диалог записи через
`/api/sessions/...`: он сценарный и вызывает сервисы реестра и расписания, но
не использует ответ LLM как шаг диалога. Ответы в сессии формирует приложение,
а не генеративная LLM. Реплики скрипта заранее заданы; ответы, выбранные врач,
свободный слот и результат визита поступают от работающего API. ASR/TTS —
заглушки: реального аудио нет. Подробная схема: [`docs/demo_checkpoint.md`](docs/demo_checkpoint.md).

## Стек и структура проекта

- **Python 3.11**, **FastAPI**, **Pydantic Settings**, **Uvicorn** — сервис и
  HTTP API; `httpx` — вызовы модели и внешнего API.
- **llama.cpp server** с OpenAI-совместимым API — опциональная локальная LLM
  (в текущей конфигурации QVikhr 8B); модель классифицирует намерения.
- **SQLite** — локальные блокировки слотов и данные планировщика напоминаний;
  **openpyxl** — импорт Excel-расписания.
- **Docker Compose** — приложение API и опциональный контейнер модели.
- **pytest** — тесты бизнес-логики.

Основные модули `app/`: `main.py` связывает FastAPI-маршруты и сервисы;
`dialogue.py` ведёт сценарии сессий; `voice.py` — текстовый голосовой
адаптер, LLM-классификацию и ASR/TTS-контракты; `registry_client.py` —
адаптер стенда с переключаемым mock/remote режимом; `mock_registry.py` —
локальная имитация стенда; `slot_manager.py` — импорт расписания и защита
слотов от двойного бронирования; `knowledge.py` — локальный extractive RAG
с источниками; `telephony.py` — текстовые сессии и эскалация; `reminders.py`
— локальный планировщик; `schemas.py` — модели запросов и ответов;
`config.py` — настройки окружения.

`docs_tz/` содержит ТЗ, регламент и входные данные (включая Excel-расписание);
`docs/` — документацию сценария; `tests/` — модульные тесты; `scripts/` —
демонстрационные и проверочные PowerShell/Python скрипты; `data/` — локальная
SQLite-база; `models/` — место для локальных моделей. Текущий MVP — текстовый
прототип, не подключённый к телефонной линии.

## Что воссоздано

### 1. Интеграция со стендом

Модуль `app/registry_client.py` содержит адаптер OpenAPI:

- `GET /doctors` — справочник врачей;
- поиск и регистрация клиентов;
- получение карточки клиента;
- создание, просмотр, перенос, отмена и завершение записи;
- создание заявки на соединение со специалистом;
- Bearer-аутентификация;
- кэш справочника врачей;
- ограничитель запросов 10 запросов в минуту;
- обработка `429`, `Retry-After`, `400`, `404`, `409`.

По умолчанию включён `REGISTRY_MODE=mock`, поэтому проект запускается без
доступа к стенду. Для подключения стенда нужно установить
`REGISTRY_MODE=remote` и указать токен в `.env`.

### 2. Slot Manager

`app/slot_manager.py` — локальный менеджер расписания:

- импортирует лист `Слоты` из Excel, используя только слоты со статусом
  `Свободен`;
- учитывает врачей, специальности, график и недоступность;
- исключает записи, уже созданные в стенде;
- создаёт локальные блокировки слотов;
- не показывает слоты деактивированных врачей;
- защищает локальный выбор слота от двойного бронирования.

В MVP используется SQLite, чтобы проект запускался без обязательной установки
PostgreSQL. В рабочем контуре SQLite можно заменить на PostgreSQL без изменения
контракта сервиса.

### 3. Безопасная диалоговая логика

`app/dialogue.py` содержит маршрутизацию намерений:

- запись;
- просмотр записи;
- перенос;
- отмена;
- справочный вопрос;
- запрос оператора;
- медицинский вопрос/симптомы;
- жалоба;
- неотложная ситуация.

Медицинские советы и назначения не генерируются. Сценарии с острой болью,
жалобой, просьбой о человеке или технической неуверенностью переводятся в
эскалацию.

### 4. Локальная телефонная заглушка

`app/telephony.py` — локальный телефонный шлюз MVP:

- создаёт входящую текстовую сессию;
- хранит историю реплик;
- завершает сессию;
- создаёт аннотацию для оператора;
- моделирует очередь оператора `100`.

Это не замена Asterisk. Это изолированный контракт, к которому позднее можно
подключить Asterisk 22/FreePBX, SIP-софтфон, AudioSocket и потоковый ASR/TTS.

### 5. Локальный mock registry

`app/mock_registry.py` воспроизводит основные правила стенда:

- командная изоляция;
- идемпотентная регистрация клиента;
- статусы `Запланирована`, `Отменена`, `Завершена`;
- запрет изменения отменённых и завершённых записей;
- запрет записи к неактивному врачу;
- отсутствие проверки занятости времени на стороне mock API.

### 6. HTTP API приложения

Основные маршруты:

- `GET /health`;
- `GET /api/doctors`;
- `GET /api/slots`;
- `GET /api/knowledge/answer?question=...`;
- `POST/GET /api/clients`;
- `GET /api/clients/{id}`;
- `POST/GET /api/visits`;
- `GET/PATCH /api/visits/{id}`;
- `POST /api/escalations`;
- `POST /api/sessions/incoming`;
- `POST /api/sessions/{id}/message`;
- `POST /api/sessions/{id}/escalate`;
- `GET /api/sessions/{id}`;
- `POST /api/admin/import-schedule`.
- `PATCH /api/clients/{id}` и полный CRUD заявок на соединение:
  `GET/POST /api/escalations`, `GET /api/escalations/{id}`.
- локальные исходящие напоминания:
  `POST /api/reminders`, `GET /api/reminders/due`,
  `GET /api/reminders/{id}`, `POST /api/reminders/{id}/result`;
- пост-обзвон с оценкой качества `POST /api/feedback`.

Проверка всех локальных API выполняется скриптом:

```powershell
.\scripts\check_api.ps1
```

Скрипт создаёт тестовые сущности в mock-контуре и проверяет их жизненный
цикл. Эти данные не отправляются во внешний стенд.

Swagger доступен на `/docs`.

## Быстрый запуск

Требования: Python 3.11+.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
Copy-Item .env.example .env
python -m uvicorn app.main:app --reload
```

Расписание для слотового сценария загружается из Excel один раз в локальное
хранилище:

```powershell
Invoke-RestMethod -Method Post `
  -Uri http://127.0.0.1:8000/api/admin/import-schedule `
  -ContentType application/json `
  -Body '{"path":"docs_tz/raspisanie_vrachey.xlsx"}'
```

Затем запустить демо: `.\scripts\demo_checkpoint.ps1`. Документация API:
`http://127.0.0.1:8000/docs`.

Импорт расписания (свободные слоты из текущего тестового Excel-файла;
прошедшие даты не показываются через API):

```powershell
Invoke-RestMethod `
  -Method Post `
  -Uri http://127.0.0.1:8000/api/admin/import-schedule `
  -ContentType application/json `
  -Body '{"path":"docs_tz/raspisanie_vrachey.xlsx"}'
```

Создание входящей текстовой сессии:

```powershell
$s = Invoke-RestMethod -Method Post `
  -Uri http://127.0.0.1:8000/api/sessions/incoming `
  -ContentType application/json `
  -Body '{"caller_id":"demo-001"}'

Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:8000/api/sessions/$($s.id)/message" `
  -ContentType application/json `
    -Body '{"text":"Хочу записаться к терапевту"}'
```

После запроса специальности ассистент попросит ФИО и дату рождения, покажет
до трёх ближайших свободных слотов и оформит выбранную запись после номера
варианта (`1`, `2` или `3`).

## Режимы

### Mock

```env
REGISTRY_MODE=mock
```

Используется для разработки и демонстрации без сети и без персональных
данных.

### Remote

```env
REGISTRY_MODE=remote
REGISTRY_API_BASE_URL=https://crm-med-mock.dbi-testing.ru/api/v1
REGISTRY_API_TOKEN=...
```

Токен не следует коммитить в Git. В текущем `.env` разрешён только тестовый
токен-заглушка.

## Справочные сценарии

`LocalKnowledgeBase` индексирует локальные `registrature_reglament.docx`,
`tz_kratkoe.txt`, `tz_voice_assistant.txt` и `openapi.json`. DOCX разбирается
как по абзацам, так и по таблицам; строка таблицы сохраняет значения вместе
с названиями колонок. Поиск использует нормализацию русского текста,
простую морфологическую нормализацию и BM25-подобное ранжирование. Ответ
возвращается только дословным фрагментом с файлом, разделом, score и
покрытием запроса — LLM не сочиняет содержимое ответа.

Сведения регламента разделены на обычные сценарии и условные справочные
значения. В DOCX адрес, часы и контакты прямо обозначены как условные, а
источником истины названы МИС и приказы. Поэтому на вопросы об актуальном
адресе, графике, стоимости и аналогичных динамических данных API не выдаёт
условную цифру/значение, а требует сверку и передачу регистратору.
Неподтверждённый вопрос возвращает `found=false`; в диалоге это ведёт к
эскалации.

Диагностика индекса доступна через `GET /api/knowledge/manifest`, поиск и
источники — через `GET /api/knowledge/answer?question=...`.

## Исходящие напоминания

Телефонный канал пока локальный текстовый. Но уже есть локальный планировщик:
напоминание привязывается к записи и caller ID, допускает не более двух
попыток, поддерживает подтверждение, отказ, просьбу о переносе и отсутствие
ответа. Подтверждение хранится локально, а отмена сразу отражается в МИС
через адаптер. Это подготовленный контракт для будущего Asterisk/SIP.

## Архитектура следующего этапа

```text
Asterisk/SIP
    |
    v
AudioSocket / ASR / VAD
    |
    v
Dialogue Orchestrator ---- RAG
    |
    +---- Registry Adapter ---- OpenAPI стенда
    |
    +---- Slot Manager -------- расписание + блокировки
    |
    +---- Telephony Adapter --- очередь оператора 100
```

На следующем этапе добавляются потоковые ASR/TTS, Asterisk AudioSocket,
локальная LLM с constrained tool calling, исходящий планировщик и
Prometheus/Grafana.

## Голосовой контур (подготовлен)

`POST /api/voice/process-text` — текстовая точка входа голосового адаптера:
правила безопасности и намерений → при необходимости локальная LLM для
классификации → безопасный ответ приложения → TTS-адаптер (сейчас stub).
LLM включается через `LLM_MODE=remote-local`; параметры контейнера и модели
описаны в `docker-compose.yml` и `VOICE_MODELS.md`. Этот endpoint не управляет
состоянием API-сессии и сам по себе не выполняет запись.

В Windows PowerShell для русских JSON-запросов используйте UTF-8 bytes:

```powershell
$body = [Text.Encoding]::UTF8.GetBytes(
  (@{text="Хочу записаться к терапевту"} | ConvertTo-Json)
)
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/voice/process-text `
  -ContentType "application/json; charset=utf-8" -Body $body
```

Для воспроизводимой проверки русских запросов напрямую к модели и через API:

```powershell
.\.venv\Scripts\python.exe -X utf8 .\scripts\probe_qvikhr.py
```

QVikhr проверена как локальный классификатор: валидный JSON на smoke-наборе,
скорость порядка 35–55 ток/с. Вопросы о лекарствах один раз были неверно
классифицированы как `unknown`, поэтому медицинские/экстренные обращения
перехватываются детерминированными правилами до LLM. Модель не используется
для выдачи фактов или медицинских ответов.

## Ограничения текущего MVP

- нет реального SIP и аудио;
- нет ASR/TTS;
- полноценный сценарий сессии работает на правилах и локальных API; отдельный
  голосовой endpoint использует локальную LLM только для классификации
  неизвестного намерения;
- реальные исходящие звонки пока не выполняются: планировщик и текстовый
  контракт готовы, но SIP/Asterisk ещё не подключены;
- подтверждение визита не имеет соответствующего статуса в OpenAPI и поэтому
  не записывается как ложный статус;
- `mock` не является заменой официальному тестовому стенду.
