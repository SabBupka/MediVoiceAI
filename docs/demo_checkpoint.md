# Сценарий демо `demo_checkpoint.ps1`

## Что показывает скрипт

Один успешный тестовый путь записи к терапевту на основе настоящих ответов
работающего приложения. Текст реплик фиксирован для воспроизводимости;
намерение, врачи, слоты, диалоговые ответы и созданный визит запрашиваются у
API во время запуска.

Скрипт продолжает работу только если `/health` отвечает `status=ok` и
`registry_mode=mock`. Для пациента используется синтетическая карточка
«Демо Тест», дата рождения `12.09.1980`, идентификатор звонка
`checkpoint-demo`. Внешний реестр не вызывается.

## Последовательность

```text
GET  /health
  └─ проверка доступности и mock-режима

POST /api/voice/process-text
  └─ фраза «Мне нужно попасть к врачу на плановый осмотр»
     └─ правила безопасности и намерений
        └─ локальная LLM классифицирует неизвестную правилам фразу
           └─ приложение выбирает безопасный ответ для intent=booking

GET  /api/doctors?specialty=терапевт
GET  /api/slots?specialty=терапевт&limit=50
  └─ выбирается врач из справочника, для которого есть слот в расписании

POST /api/sessions/incoming
POST /api/sessions/{id}/message  (несколько реплик)
  └─ сценарий просит и подтверждает синтетические данные пациента
  └─ показывает подходящих врачей и доступное время
  └─ пациент выбирает слот и подтверждает запись
     └─ приложение регистрирует пациента в mock-реестре
     └─ Slot Manager проверяет и резервирует слот
     └─ приложение создаёт визит в mock-реестре

GET  /api/clients
GET  /api/visits?client_id=...
  └─ проверка созданной карточки и записи
```

## Важное разделение компонентов

`/api/voice/process-text` и `/api/sessions/.../message` — два отдельных
маршрута текущего MVP. Первый демонстрирует текстовый голосовой адаптер и
LLM-классификацию. В нём модель возвращает только намерение, например
`booking`; текст реплики пациенту берётся из безопасных ответов приложения.
Модель не формирует свободный ответ и не вызывает инструменты записи.

Второй маршрут ведёт состояние диалога записи и вызывает текущие сервисы
реестра, расписания и бронирования. Диалог в сессии сценарный и rule-based:
LLM-классификатор из `process-text` не встроен в этот путь. Реплики пациента
в демо предзаданы, а ответы ассистента и результат записи не захардкожены.

ASR и TTS сейчас работают в режиме `stub`: скрипт передаёт текст вместо
аудио, синтезированный звук не возвращается. Скрипт создаёт демонстрационные
данные; повторные запуски используют ту же синтетическую карточку и могут
создавать новые визиты на следующих свободных слотах.

## Данные расписания

Источник расписания — `docs_tz/raspisanie_vrachey.xlsx`. `SlotManager`
импортирует свободные строки листа `Слоты` в SQLite, а `GET /api/slots`
показывает только будущие и незаблокированные слоты. Перед демо расписание
нужно загрузить через `POST /api/admin/import-schedule`; команда приведена в
README. Если у терапевтов нет активных врачей со свободными слотами, сценарий
останавливается вместо того, чтобы выдумывать расписание.

## Реализованный стек

- PowerShell 5.1+ — оркестрация демо, UTF-8 JSON-запросы и вывод этапов.
- Python 3.11, FastAPI, Pydantic Settings и Uvicorn — HTTP-приложение.
- llama.cpp server с OpenAI-совместимым endpoint — опциональная локальная
  LLM-классификация.
- `httpx` — запросы приложения к LLM и remote-адаптеру реестра.
- `openpyxl` — чтение расписания Excel; SQLite — расписание, блокировки и
  локальные данные напоминаний.
- Docker Compose — API и опциональный контейнер модели; pytest — тесты.

## Связанные файлы

- `scripts/demo_checkpoint.ps1` — исполняемый демонстрационный сценарий.
- `app/main.py` — HTTP-маршруты и связывание сервисов.
- `app/voice.py` — безопасный маршрут, LLM-классификатор и TTS/ASR-контракты.
- `app/dialogue.py` — распознавание намерений, сущностей и шаги диалога.
- `app/registry_client.py`, `app/mock_registry.py` — интерфейс реестра и mock.
- `app/slot_manager.py` — импорт и резервирование слотов.
- `docs_tz/raspisanie_vrachey.xlsx` — источник тестового расписания.
